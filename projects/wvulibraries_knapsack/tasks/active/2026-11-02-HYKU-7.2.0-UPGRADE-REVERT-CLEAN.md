## Background

**Current Issue** (hykudev, post-Oct 29 7.2.0 upgrade):
- Valkyrie indexer writes to: UUID collection (`c7998894-fea0-4f54-bfb7-3d4a0ae40b25`, 4,727 docs)
- Rails search queries: `hydra-production` collection (0 docs, empty)
- Result: Facets load but document results pane blank
- Discovered during Friday Oct 30 testing after Thursday Oct 29 upgrade
- **Reindexing attempt (Oct 30)**: Tried to fix via re-indexing but issue persisted (collections remained diverged)

**Key Discovery**: UUID collection pre-exists on hykudev
- Local testing shows 7.1.3 and 7.2.0 don't auto-create UUID collections (both use standard collections)
- UUID collection on hykudev is pre-existing (could be from earlier upgrade attempts or configuration issues)
- Likely masked by ActiveFedora indexer in 7.1.3, exposed by Valkyrie in 7.2.0
- Simple reindexing didn't resolve the divergence (root cause is collection misconfiguration, not just missing data)

**Local Testing Result**:
- 7.1.3 local: Standard collections only (`hydra-development_shard1_replica_n1`, no UUID)
- 7.2.0 local: Same standard collections (no UUID auto-created)
- Conclusion: UUID collection is pre-existing on hykudev (pre-dates Oct 29 upgrade)

**Why This Plan Works**:
- Oct 29 1:20 PM snapshot is pre-upgrade (clean baseline before Oct 29 afternoon upgrade)
- Revert → fresh data import → fresh upgrade will show if bug reproduces on clean state (code issue) or was environmental from pre-existing UUID
