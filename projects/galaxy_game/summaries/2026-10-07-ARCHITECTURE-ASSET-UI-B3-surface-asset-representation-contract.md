## B3 — Define Surface Asset Representation Contract

### 1. What Canonical Information a Surface Renderer Needs to Resolve a Unit Asset

**Evidence from A5 findings:** SurfaceView.js has a terrain tile pipeline but no functional unit sprite loading. KNOWN_ASSETS is an empty Set. Unit-layer grid data exists but does not resolve unit IDs to sprites. No sprite sheets, animation frames, or damage states are modeled/consumed. BiomeRenderer demonstrates an existing PNG-fetch/fallback pattern for terrain assets (functional for terrain only).

**Evidence from A3 findings:** RH-400 has one existing RGBA sprite-test candidate (rh400_sprite_test.png, 1536x1024, RGBA) that is explicitly a test/experimental asset. Visual Definition specifies six render profiles but only three files exist. Prompt template Pass 1 specifies transparent-background surface sprites, animation frames, and damage states.

**Required canonical information for surface renderer:**

| Field | Source | Required? | Purpose |
|-------|--------|-----------|---------|
| asset_id | Visual Definition (REQUIRED) | YES | Shared canonical identity; primary key for sprite lookup |
| asset_family | Visual Definition (REQUIRED) | YES | Determines asset family path construction |
| component_class | Visual Definition (REQUIRED for units/structures/vehicles) | YES | Determines component-specific sprite paths |
| surface_sprite_path | Pre-computed manifest (from development-time orchestration) | YES | Path to the base surface sprite PNG |
| animation_states | Pre-computed manifest (from development-time orchestration) | Conditional | Array of animation state paths for dynamic rendering |
| damage_states | Pre-computed manifest (from development-time orchestration) | Conditional | Object mapping damage levels to sprite paths |
| sprite_dimensions | Development-time metadata | YES | Width x height of the base sprite for correct positioning |
| transparency | File format (RGBA PNG) | YES | Surface sprites MUST have transparent background |

### 2. How Unit Identity Maps to Surface Representation(s)

**Evidence from B1 findings:** The registry stores asset_id as primary key, blueprint_id for canonical game data identifier, and file_prefix for filesystem naming convention. RH-400 has three identifiers: regolith_harvester_rover (blueprint), VEHICLE_HARVESTER_ROVER_RH400 (asset_id), rh400_ (file prefix).

**Evidence from VISUAL_CONTRACT.md v1.0:** "asset_id is a shared identity, not a file path." Development-time orchestration determines which Visual Definition, Visual Profile, and Render Template apply for a given asset_id.

**Proposed surface representation identity mapping:**

| Surface Asset Type | Path Construction | Example (RH-400) |
|-------------------|------------------|-----------------|
| Base surface sprite | /assets/sprites/{asset_family}/{file_prefix}_sprite.png | /assets/sprites/vehicles/rh400_sprite.png |
| Animation frames | /assets/sprites/{asset_family}/{file_prefix}_anim_{state}_{frame}.png | /assets/sprites/vehicles/rh400_anim_idle_01.png |
| Damage states | /assets/sprites/{asset_family}/{file_prefix}_damage_{level}.png | /assets/sprites/vehicles/rh400_damage_03.png |
| Sprite sheet | /assets/sprites/{asset_family}/{file_prefix}_spritesheet.png | /assets/sprites/vehicles/rh400_spritesheet.png |

**Surface renderer lookup flow:**

```
SurfaceView.js receives: { unit_id, position, state }
  -> Looks up in surface_manifest: surface_manifest[unit_id]
  -> Gets: { asset_id, sprite_path, animation_states[], damage_states{}, dimensions{} }
  -> Fetches PNG from sprite_path (via manifest path, NOT repository search)
  -> Renders on terrain with transparent background
```

**Key constraint:** The surface renderer does NOT perform repository search by asset_id or unit_id. All paths come from a pre-computed manifest generated by development-time orchestration.

### 3. How Static Sprites, Sprite Sheets, Animation Frames, and Damage States Should Be Distinguished at the Contract Level

**Evidence from A3 findings:** Prompt template Pass 1 specifies transparent-background surface sprites, animation frames, and damage states as distinct render profiles. Visual Definition's render_profiles field includes sprite_sheet as one of six planned profiles.

**Proposed contract-level distinction:**

| Representation Type | Visual Definition Field | Surface Renderer Usage | Technical Requirements |
|-------------------|------------------------|----------------------|----------------------|
| Static sprite | render_profiles: ["surface_sprite"] (proposed new profile) | Base unit rendering on terrain | Transparent PNG. Single frame. Dimensions TBD. |
| Sprite sheet | render_profiles: ["sprite_sheet"] (existing from Visual Definition) | Animation frame extraction | Multi-frame PNG with known layout. Each frame has fixed dimensions. |
| Animation frames | render_profiles: ["animation_frames"] (proposed new profile) | State-based animation | Individual PNG files per frame. Known cycle timing from animation_profile. |
| Damage states | render_profiles: ["damage_states"] (proposed new profile) | Damage-based visual switching | Individual PNG files per damage level. Same dimensions as base sprite. |

**Key principle:** Each representation type is a distinct contract with its own technical requirements. The surface renderer selects the appropriate type based on game state (idle -> static sprite, moving -> animation frames, damaged -> damage states).

### 4. How Transparent-Background Assets Are Represented/Located

**Evidence from A3 findings:** RH-400 sprite test (rh400_sprite_test.png) is RGBA with transparent background - suitable for surface sprite but explicitly experimental. Prompt template Pass 1 specifies "transparent-background surface sprites."

**Proposed contract:**

| Requirement | Specification |
|------------|---------------|
| Format | PNG with RGBA channels (alpha channel REQUIRED) |
| Background | Transparent (alpha = 0) for all non-catalog assets |
| Dimensions | TBD by C-series implementation; must be consistent across all representations of the same asset |
| Location | Pre-computed manifest path (NOT repository search) |
| Validation | Development-time tooling validates RGBA format and transparency before marking representation as "exists" |

**Key principle:** Surface sprites are ALWAYS transparent. The surface renderer composes the terrain background dynamically based on terrain type, lighting, and game state. NO baked backgrounds in generated assets.

### 5. What Runtime Data Belongs in the Surface Renderer vs. Development-Time Asset Registry/Orchestration

**Evidence from A5 findings:** SurfaceView.js has empty KNOWN_ASSETS. Unit-layer grid data exists but does not resolve unit IDs to sprites. BiomeRenderer demonstrates PNG-fetch/fallback pattern for terrain (functional for terrain only).

**Proposed separation:**

| Data | Domain | Owner |
|------|--------|-------|
| Sprite file paths | Development-time | Asset Registry/orchestration generates manifest |
| Animation state definitions | Development-time | Visual Definition + ProfileResolutionEngine |
| Damage state definitions | Development-time | Visual Definition + ProfileResolutionEngine |
| Pre-computed surface manifest | Development-time -> Runtime bridge | Generated by orchestration, bundled with game |
| Sprite loading/fetching | Runtime | SurfaceView.js (fetches from manifest paths) |
| Terrain composition | Runtime | SurfaceView.js (composes sprites on terrain) |
| Animation timing/cycling | Runtime | SurfaceView.js (uses timing from manifest) |
| Damage state switching | Runtime | SurfaceView.js (switches based on game state) |
| KNOWN_ASSETS population | Development-time -> Runtime bridge | Pre-computed manifest populates KNOWN_ASSETS at startup |

### 6. How Missing/Unavailable Surface Representations Should Be Handled

**Evidence from A5 findings:** No functional unit sprite loading exists. KNOWN_ASSETS is empty. No sprite sheets, animation frames, or damage states are modeled/consumed. BiomeRenderer has PNG-fetch/fallback for terrain only.

**Proposed fallback behavior:**

| Representation | Missing Status | Fallback |
|---------------|---------------|----------|
| Base surface sprite (MISSING) | No sprite exists for asset | Unit renders as empty grid cell or placeholder marker on surface |
| Animation frames (MISSING) | No animation data exists | Static sprite displayed; no animation cycling |
| Damage states (MISSING) | No damage data exists | Base sprite displayed at all damage levels |
| Sprite sheet (MISSING) | No sprite sheet exists | Individual frame files used instead (if available) |

**Fallback principle:** Missing surface representations result in graceful degradation:
- No base sprite -> empty/placeholder on surface (NOT a crash, NOT a broken image)
- No animation -> static display (acceptable for early development)
- No damage states -> uniform appearance at all damage levels

**Key constraint:** The surface renderer does NOT fabricate assets, promote test assets, or use catalog renders as surface sprites. Absence is handled by placeholder rendering.

### 7. Whether the Existing Terrain PNG Loading Pattern Is Reusable as a Conceptual Pattern

**Evidence from A5 findings:** BiomeRenderer demonstrates an existing PNG-fetch/fallback pattern for terrain assets - functional for terrain only. It loads 12 PNGs from /assets/biomes/ and has working PNG fetch + solid-colour fallback.

**Proposed answer: YES, as a conceptual pattern, with modifications.**

| Pattern Element | BiomeRenderer (Terrain) | Surface Renderer (Units) | Reusable? |
|----------------|------------------------|-------------------------|-----------|
| PNG fetch from /assets/ path | Works for terrain | Would work for sprites | YES - same fetch mechanism |
| Solid-color fallback | Terrain uses color when PNG missing | Surface needs placeholder, not solid color | PARTIAL - fallback type differs |
| KNOWN_ASSETS Set | Empty (surface) | N/A (terrain has biome registry) | NO - surface needs population |
| Asset path construction | /assets/biomes/{biome_name}.png | /assets/sprites/{family}/{prefix}_sprite.png | YES - same pattern, different paths |

**Reusable pattern from BiomeRenderer:**

```javascript
// BiomeRenderer pattern (terrain)
const biomeImages = {};
for (const biome of BIOME_NAMES) {
  const img = await fetch(`/assets/biomes/${biome}.png`);
  biomeImages[biome] = img;
}

// Surface renderer adaptation (conceptual)
const surfaceSprites = {};
for (const assetId of KNOWN_ASSETS) {
  const spritePath = surfaceManifest[assetId].surface_sprite.path;
  const img = await fetch(spritePath);
  surfaceSprites[assetId] = img;
}
```

**Key modification:** Surface renderer needs a pre-computed manifest to populate KNOWN_ASSETS (currently empty). BiomeRenderer has hardcoded biome names; surface renderer needs dynamic asset discovery via manifest.

**Evidence from A3 findings:** rh400_sprite_test.png is RGBA, 1536x1024, explicitly a test/experimental asset. It is NOT a production surface sprite.

**Proposed classification:**

| Property | Value | Classification |
|----------|-------|---------------|
| File | data/images/catalog/crafts/ground/rh400_sprite_test.png | Existing file |
| Format | RGBA (transparent background) | Technically suitable for surface sprite |
| Status | Experimental/test | NOT a production asset |
| Dimensions | 1536x1024 | Too large for typical game sprite; needs downscaling |
| Contract role | None | Does NOT map to any contract representation type |

**Classification: EXPERIMENTAL - NOT PRODUCTION**

The RH-400 sprite-test asset has the technical characteristics of a surface sprite (RGBA, transparent background) but is explicitly experimental. Under the proposed contract:
- It is recorded in the Asset Registry's representation manifest as status: "experimental"
- It is NOT used as a production surface sprite
- It is NOT promoted to production status without explicit C-series implementation
- It serves as a visual reference for what a production RH-400 surface sprite should look like

### Proposed Surface Asset Representation Contract

**Surface representation types:**

```
SurfaceRepresentation {
  // Identity
  asset_id: string (REQUIRED, shared canonical identity)
  blueprint_id: string (REQUIRED, canonical game data identifier)
  
  // Base sprite
  surface_sprite: {
    path: string (REQUIRED, from pre-computed manifest)
    dimensions: { width: integer, height: integer } (REQUIRED)
    transparency: "rgba" (REQUIRED, always transparent)
    status: "exists" | "missing" | "experimental" (REQUIRED)
  }
  
  // Animation states (optional - populated when available)
  animation_states: [
    {
      state: string ("idle" | "moving" | "harvesting" | ...) (REQUIRED)
      frames: string[] (paths to individual frame PNGs)
      cycle_timing: string ("0.5-1s", "2-3s", etc.) (REQUIRED)
    }
  ]
  
  // Damage states (optional - populated when available)
  damage_states: [
    {
      level: integer (0 = pristine, N = maximum damage) (REQUIRED)
      path: string (REQUIRED, from pre-computed manifest)
    }
  ]
  
  // Sprite sheet (optional - alternative to individual frames)
  sprite_sheet: {
    path: string | null
    frame_count: integer | null
    frame_dimensions: { width: integer, height: integer } | null
    layout: "grid" | "strip" | null
  }
  
  // Overall status
  status: "complete" | "partial" | "missing" (REQUIRED)
}
```

### Surface vs. Catalog Asset Separation

| Property | Catalog Assets | Surface Assets |
|----------|---------------|---------------|
| Background | Opaque (white for catalog renders) | Transparent (RGBA PNG) |
| Purpose | Documentation/UI display | Gameplay rendering on terrain |
| Consumer | CatalogController + frontend JS | SurfaceView.js (gameplay renderer) |
| Path source | Pre-computed catalog manifest | Pre-computed surface manifest |
| Update cycle | When asset is rendered/generated | When asset is rendered/generated |
| Runtime Rails dependency | None (manifest bridge) | None (manifest bridge) |
| Development-time tooling | PromptCompiler generates renders | PromptCompiler generates sprites |

### Unresolved Questions

1. **Sprite dimensions** - What are the target dimensions for surface sprites? RH-400 sprite test is 1536x1024 but this may be too large for game use.
2. **Animation state taxonomy** - What animation states exist for each asset family? The Icon Bible Section 9 rules provide categories (vehicles -> status lights) but not a complete state taxonomy.
3. **Damage state granularity** - How many damage levels per asset? What visual changes occur at each level?
4. **Sprite sheet layout** - If sprite sheets are used, what is the grid layout (rows x columns)?
5. **Manifest delivery mechanism** - How surface_manifest is delivered to runtime (bundled JSON? API endpoint?) is an implementation detail for C-series.
